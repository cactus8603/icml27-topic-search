## 必修（會動到判準，交使用者／Fable 定案，我沒有改）

### 必修 1：主指標的距離空間與 t 加權要在凍結前寫死
- 53 和 56 的「分數距離」指的是 ε（score）預測的 cosine。CelebA 這邊確實用 ε-space，但階層資料改用 **x0-hat 機率向量**的 `1−cos`。cosine 在仿射轉換下不守恆：ε = (x_t − √ᾱ·x̂0)/√(1−ᾱ) 含有兩個模型共用的 x_t 項，所以兩種空間的最低點 epoch 可能不同。
- x0-hat 是非負的機率向量，彼此天生就很相近（cos 偏高），訊號會被壓縮。
- 主指標先在 8 個 t 上平均原始的 `1−cos`，再找最低點。這樣量級最大的 t（通常是大 t）會主導 t\*。實測中，乾淨葉節點可以 100% 還原根符號，所以小 t 時 p_cond ≈ p_uncond，CFG 的差異只在中、大 t 出現。也就是說，t 怎麼加權會直接左右結果。
- 建議三選一後寫進 PREREG 與 criteria json：(i) 改成 ε-space（與 53/56、CelebA 一致；程式改動很小，`eps_hat = (x_t − √ᾱ·x̂0)/√(1−ᾱ)`）；(ii) 保留 x0-hat，但說明理由並經使用者確認；(iii) 每個 t 的曲線先除以自身跨 epoch 的平均再平均，或改成平均 log 距離。**不要兩種都算、看完結果再挑**，那就是擇優。

### 必修 2：t\* 落在網格邊界（設限）時的判讀規則
- PREREG 閘門 3 只寫「要標記」，沒有說標記後怎麼處理。我已補上標記功能（見「已修」），但判讀規則還沒定。
- (a) 的漏洞：如果距離曲線單調上升，沒有 U 形，e_bias_min 會落在第一格（epoch 10），log(e_loss/e_bias) 就會變得很大，反而**錯誤地通過**重現閘門。建議規定：任何模型的 e_bias_min 或 e_testloss_min 落在網格頭尾，該模型就算「未重現」；有 2 個以上這種模型，(a) 記為未能測試。
- (c) 的漏洞：如果 cond 或 cfg3 的曲線沒有內部最低點，t\* 會被設限，比值可能是 0（兩者都在最後一格）。這種情況可能被當成 FAIL 帶，或剛好落在 ±10% 內。建議規定：設限的模型對超過 1/3 時，主指標記為「未能測試（無偏差期）」，不得判為 FAIL；並把「cond 分支有內部最低點的比例」加進第 1 週 (b) 的閘門，作為管線與設定確實能進入偏差期的證據。

### 必修 3：n=70000 負控制的前提不成立，成本也超出預算
- **前提問題**：K=6 時，n=70000 的條件分支每類約有 11,667 筆，正好落在原作 n=12000 的範圍，而原作的主要偏差泛化例子（Fig. 1b、4）就是 n=12000。依本題假設，n=70000 的條件分支本來就**應該**進入偏差期，CFG 也應該放大它。所以「各 w 之間不應有差」在假設成立時反而會不過，會被誤判成「實作有 bug」。這不是一個虛無控制。
- **成本**：每個 epoch 需 ⌈70000/512⌉=137 步，35000 epochs 約 4.8M 步，是 n=5000 的 24 倍。依 README 對 n=5000 每步 7.5–15 ms 的推估，每個模型約 10–20 GPU-h。至少要 2 個模型，若要有 CI 則需 6 個，合計 20–120 GPU-h，會吃掉或超過前兩週 115 GPU-h 的總上限。縮短 epoch 也救不了前提問題。
- **建議改成 K=1 負控制**：同樣 n=5000、pdrop=0.1，但所有樣本的條件都設成同一個標籤（常數條件）。這時 n/K=n，假設預測兩個時鐘沒有差別，CFG 只剩算術效果（再加上無條件分支只拿到 10% 更新的效應）。主指標的 CI 應落在 ±10% 內；有差就代表指標或「CFG 算術、更新比例」本身會製造假訊號。成本等於一般 n=5000 的 run（每個 1.5–3 h），建議 3–6 個 run。
  - 程式要改：`train_hier_cond.py` 加 `--const-label`；`eval_hier_oracle.py` 對這類 run 的條件 oracle 要用無條件 BP（根先驗均勻），模型條件輸入則用常數標籤。
- 這是修改 56 號報告的閘門，需要使用者或 Fable 確認。

### 必修 4：正控制的資料定義與容許範圍
- 現在的寫法是 `--n 833 --pdrop 1.0`，取的是該區塊**前 833 筆混合各類**的資料。但條件分支 c 在建模的是 P(x|c)，用 n/K 筆**同一類**的樣本。比較對象應該是「只用類別 c 的約 833 筆訓練的無條件模型」，條件分支的 t\* 也只在類別 c 的輸入上計算。
- 每個區塊每類約有 764–874 筆，可以從 pick 0–5 各取類別 0 組成 6 個不相交的模型，共 15 對；每個模型每 epoch 只有 2 步，成本約是 n=5000 的 1/5。
- `eval_hier_oracle.py` 用 `metas[0]["n"]` 和 `p*n` 切區塊，不支援 n 不同或依類別抽取的 run，要先改。
- 單看 ±25%（|Δlog t\*| ≤ log 1.25）不夠，必須先確認這個控制有分辨力。建議另訓 n=5000、pdrop=1.0 的純無條件模型（剛好也可當作原作 n=5000 設定的重現對照），並要求：(1) |log t\*_u(5000) − log t\*_u(833)| ≥ 2·log 1.25，否則記「控制無分辨力」；(2) 條件分支的位置 λ = log(t\*_c/t\*_u5000) / log(t\*_u833/t\*_u5000) 以模型 bootstrap 計算，95% CI 下界 ≥ 0.5（較接近 n/K 時鐘），且 |log(t\*_c/t\*_u833)| ≤ log 1.25。
- 不要拿條件模型裡的無條件分支當 n 時鐘：它只拿到 10% 的更新，時鐘本來就會變慢。

## 實作者待審點逐項判斷

### 1. (a) 重現判讀方式
- **合理，可當閘門用。** 逐模型計算 log(e_loss/e_bias)，用模型間 SEM、n=6，要求平均 > 2·SEM 且 > 0。在 df=5 下大約相當於單尾 p≈0.05，偏寬鬆，但這只是管線閘門，不是假設檢定，可以接受。
- 有兩個缺陷：
  - 每個模型的 e_bias 都用到其餘 5 個模型，6 個值彼此不獨立，SEM 會偏小。建議在 info 中另外輸出以模型為單位的 bootstrap CI，只描述、不判定。
  - 邊界漏洞（見必修 2）。這一點必須補上。
- **能否分辨 pipeline 問題與現象本身不穩**：光靠現有設計不行。建議在 PREREG 預先寫好「失敗時的診斷樹」，只在 (a) 不過時執行，不算翻盤重跑：
  1. 先看形狀：test loss 有沒有內部最低點，距離曲線有沒有 U 形。沒有的話，先查訓練（loss 量級是否與原作相近）。
  2. **評估碼交叉核對**（幾乎不花 GPU）：本包的 checkpoint 目錄命名沿用原作慣例（`CelebA32_1024_32_Adam_512_0.0001_index{i}/Models/Model_epoch_*`），可以直接用原作的 `compare_scores.py -t 50/150` 跑同一對模型，和 `eval_celeba.py` 的結果比對。
  3. **訓練碼交叉核對**（約 1–2 GPU-h）：用原作 `run_Unet.py` 的 standard 模式（`-i k -se k --epochs 5000`）訓 2 個模型，再用本包的 eval 評估。如果原作訓出來的模型也不過，代表是現象或設定（6 個模型、分數層級）不穩，不是本包的程式問題；如果原作的模型過了、本包的不過，就是 `train_celeba.py` 有問題。
- 補充：原作論文的主要證據是樣本層級；分數層級在 t=50、150 最明顯。本包用的是分數層級 t∈{50,100,150}，與原作的 `compare_scores.py` 一致。

### 2. 階層資料距離只用兩份訓練集的輸入
- **合理。** sample-split 偏差本來就定義在訓練樣本上。用 S_i 與 S_j 兩份是對稱的，每份各有一個模型看過、一個沒看過，測試輸入留作次要指標也正確。
- 補充：每個訓練區塊和測試區塊 7 之間有 22–27 筆完全相同的序列（整份資料共 532 筆重複）。原作也一樣，影響很小，但寫論文時要提。真正的問題是距離所在的空間，見必修 1。

### 3. 負控制成本與正控制容許範圍
- 負控制不只是成本問題，前提本身就不成立，必須改設計，見必修 3。建議改成 K=1 的常數條件負控制。
- 正控制的 ±25% 可以當作「接近」的容許範圍，但必須同時要求控制有分辨力，資料也要改成單一類別，見必修 4。

### 4. 第 1 週只有 3 個 run
- 同意標為探索性；aggregate 已在 R<6 時輸出 status_note。R=3 時有 11% 的 bootstrap 抽樣只抽到同一個模型而被跳過，CI 沒有意義。
- 需要守住兩件事：
  - 第 2 週的 pick 3–5 必須用同一份凍結的程式與設定訓練，再把 6 個 run **一起**重新評估。噪聲輸入取決於 run 的順序與數量，不能把兩次評估結果拼在一起。
  - 第 1 週看到的探索性主指標，不得拿來調整第 2 週的任何設定。

### 5. 與原作的差異
| 差異 | 判斷 |
|---|---|
| eval 用 1024 張、共同 mean 中心化 | **不失真**。原作 `compare_scores.py` 也用單一 mean。6 個區塊的平均亮度在 0.432–0.446 之間，差距約 0.007，遠小於噪聲尺度。輸入張數增加只會降低雜訊。 |

| 階層 transformer | 與原作 `create_model` 相同：8 層、512、4 head、ff=1024、dropout 0.1、t~U{1..500}、CE、lr 3e-4、'default' LR 排程、batch 512。差別是加了類別嵌入，並與時間嵌入一起加到所有 token 上。 |

## 其他檢查項目

- **主指標實作**：`pair_cos[p][:, :, :2, b]` 取兩份訓練輸入，先在 t 上平均，再做 3 點置中移動平均（邊緣縮窗），取 argmin 的 epoch，最後算 log(t\*_cfg3 / t\*_cond)。CFG 在 x0-hat 空間計算為 `(1+w)p_c − w p_u`，w=0 時等於條件分支，與單元測試 T6 一致。cfg3 是用模型輸出的 softmax 組合而成，oracle 也用同一個式子 ✓。
- **bootstrap**：以模型為單位，有放回地抽 R 個，只保留兩端都在樣本中的模型對，再取平均（每對不依重複次數加權），與 PREREG 的描述一致 ✓。建議（非必修）：改成依 m_i·m_j 加權，這才是 U 統計量標準的模型層級 bootstrap。這會動到 CI 的算法，所以要在凍結前決定。
- **門檻和 56 號報告的一致性**：(c) PASS 為平均 ≤ log 0.8 且 CI 上界 < 0；FAIL 帶為 CI ⊂ (−log 1.1, log 1.1)；灰區只准加跑 n_c=100 一次；「其他組合」交人工判讀 ✓。56 的「提早至少 20%」被解讀成點估計，而不是 CI 上界 ≤ log 0.8，這個解讀合理，PREREG 也寫明了。aggregate 只讀 json 的數字，判定是機械式的 ✓。第 1 週 overall 不使用 c_pass，這是正確的。
- **閘門命名**：aggregate 的 `G3_hier_oracle_curves` 和 PREREG 的閘門 3（雜訊底線）不是同一件事，只是名字容易混淆，不影響判定。
- **BP**：`results/bp_unit_test.json` 全部通過。我另外確認了資料檔的文法 M 與 T3 所用的完全相同（差 0.0）；在 2000 筆乾淨葉節點上做 BP，根符號 100% 還原，結果都是有限值。

### sbatch、環境與磁碟
