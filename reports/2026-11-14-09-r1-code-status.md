### 1. 程式架構與資料流（已驗證，讀過原始碼）

**Rollout 產生：`src/r1_run.py`**

**Microbench：`r1_run.py:80-103`**

**排程：`src/r1_policy.py`**

  1. microbench（pre）

### 5. 程式問題

**可能的 bug 與流程缺口：**
1. **runner 設定只寫在送出腳本：** `VLLM_USE_V2_MODEL_RUNNER=0` 只在 `submit-h200-w2.sh:23` 和 `r1_replay.py:228` 設，`r1_run.py:32-34` 沒有。如果有人不透過送出腳本直接跑 `r1_run.py`，生成會用 V2 runner、重播用 V1，兩邊的步時就對不起來。
2. **V1 runner 從沒跑過：** W1r、W1r2 都是 V2 runner。W2 換成 V1 之後，`r1_sched` 的記錄和每條 seed 的取樣都還沒在真實 GPU 上驗證過。
3. **8B 放不下時不會停：** smoke 和正式跑在同一個 job 裡接著執行（`submit-h200-w2.sh:27-31`），中間沒有地方讓人照卡上 §9「kv_cap 不夠就改 24 條」去改。真的放不下時只會印 WARNING 然後照跑，結果是出現 preemption、3a 不過。
4. **下界的 KV 位置不完全對齊：** `r1_w2_analyze.py:309` 用 pre microbench 的格子 KV，但步時表取的是 pre、post 逐格的較小值。偏差很小，對下界影響可忽略。
5. **沒有符合條件的批次時直接判 NO-GO：** `P2prime_ok` 在「沒有任何留出批的天真估計 ≥ 0.1」時會是 False，判定就直接變 NO-GO（`r1_lb2.py:121`）。這是邊界情況。

**模擬與真實 serving 之間沒驗證的假設：**
- **T 不是 wall-clock：** T 是步內 dt 的總和，不含排程器、add_request、輸出處理的 CPU 時間。主張講的是「rollout 時間」，但量的是 GPU 步時，審稿人很可能會問。`wall_s` 有記，建議至少一起報。
- **仿射下界只在量過的格子上驗證：** 8B 在長 context 下只量得到 b ≤ 32，大 b 的長 context 都是外插。
- **microbench 與實際取樣不同：** microbench 用 greedy、不帶 seed，rollout 是 temperature 1.0、每條帶 seed，取樣成本不同。b0、b1 的校準 c 會吸收這個差，對下界則是偏保守。
- **跨 job 換卡：** 重播 job 和生成 job 可能落在節點上不同的 GPU（8 張共用），V3「seq 跟生成相差 ≤ 5%」可能因為卡與卡之間的差異而不過。
- **共用節點的 CPU：** 節點 CPU 已配出 112/128。`dt` 不含 CPU 排程時間，但 sampler 和 launch 仍可能受影響。時脈只記了 GPU 的。
- **8B 的取樣設定：** 8B 用 T=1.0、top_p=1、沒有 top_k，不是 Qwen 建議的 0.6、0.95、20。我讀了 vLLM 原始碼：使用者自己給 SamplingParams 時，不會套 generation_config 的預設。結果可能是截斷比例上升；超過一半的批次，P2′ 等於沒被檢驗到。

**重現性：**
- job 25532 跑的時候 `repo_dirty: 3`，程式是事後才補提交的（commit 011dad2）。
- 生成 trace 本身沒辦法 bit 級重現（BF16、batch 組成會影響輸出），所以只能靠保存下來的 trace，重播也只保證長度相同。
- 程式沒有指定模型 revision，只靠本機路徑。

**缺少的測試：**
- 沒有任何真實 vLLM 的重播整合測試，只有假引擎。
- 沒測過 V1 runner 下 `r1_sched` 的欄位是否正確。
- 沒測過 8B 的 KV 容量。
- 沒有測 `r1_analyze.py` 本身數值的單元測試，只有自測第 4 項端到端間接涵蓋。
