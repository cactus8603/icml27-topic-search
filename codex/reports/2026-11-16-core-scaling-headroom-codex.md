# CORE 2B 升級 8B 後，改善空間是否消失？

[codex] 2026-11-16，台北。使用者授權的實際量測已完成，獨立結果審查 PASS。以下數字由凍結分析 JSON 直接格式化；這是已曝光開發面板的診斷，交由使用者判斷研究方向。

**本輪 CORE 2B→8B 升級沒有吃光改善空間。** 固定 2B 召回，只換 8B 重排，mAP 從 55.42 升到 59.88，增加 4.46 個百分點，95% CI [1.17, 7.79]。它回收原排序差距的 **23.1%**，95% CI [6.81, 37.98]%；大部分原排序差距仍存在。

同時升級召回與重排的 mAP 是 56.37，只比原基線高 0.95 個百分點，95% CI [-4.12, 5.90]，尚未證明穩定提升。它距離自己的固定候選 oracle 還有 **15.13 個百分點**，95% CI **[10.45, 20.18]**。

## 四格結果與上限定義

同一批 8,191 張圖、136 題，兩種召回都先對完整圖庫排序，每題各取前 50 張重排；未入池圖片保留該召回模型原尾序。完整圖庫 mAP 以全部正例為分母，並非 AP@50。所有格皆使用官方完整權重、BF16、相同提示與影像設定。

| 召回／重排 | mAP % | Recall@50 % | 固定候選 oracle mAP % | 剩餘排序差距 pp | 前 50 無正例題數 |
|---|---:|---:|---:|---:|---:|
| 2B／2B | 55.42 | 74.51 | 74.75 | 19.32 | 30 |
| 2B／8B | 59.88 | 74.51 | 74.75 | 14.86 | 30 |
| 8B／2B | 53.55 | 71.20 | 71.50 | 17.95 | 32 |
| 8B／8B | 56.37 | 71.20 | 71.50 | 15.13 | 32 |

這裡的 oracle 是利用評估標籤，把**目前入池 50 張**的正例全部移到前面，池外尾序保持原狀。它衡量固定候選下的排序上限，沒有解決漏找。換召回模型須重算 oracle，因此 8B 的上限不能沿用 2B 的 74.75。所有題的標記正例均不超過 50 張，Recall@50 的容量上限為 100%。

## 大模型回收多少？

| 配對比較 | mAP 增益 pp | 95% CI |
|---|---:|---:|
| 只換重排：2B／8B − 2B／2B | +4.46 | [1.17, 7.79] |
| 只換召回：8B／2B − 2B／2B | -1.87 | [-6.35, 2.43] |
| 同時升級：8B／8B − 2B／2B | +0.95 | [-4.12, 5.90] |
| 8B 入池換重排：8B／8B − 8B／2B | +2.82 | [-0.43, 5.99] |
| 8B 重排換召回：8B／8B − 2B／8B | -3.51 | [-7.43, 0.03] |

原 2B 池排序差距為 19.32 pp，8B 重排回收 4.46 pp，比值 23.08%；升級後同池仍剩 14.86 pp。比例是平均增益除以平均原差距，區間使用同一批配對群重抽。

8B 召回的 Recall@50 點估較低，但其與 2B 的差值區間跨零，不能宣稱已證明 8B 普遍退步。**本四格中最高 mAP 是 2B 召回＋8B 重排**，適合作為下一階段的較強工作基線；這不代表全領域 SOTA，也不證明任何新方法有效。

## 事前判準與仍存在的差距

不確定性以「同原群或共享任一正例」形成的 110 個連通群作 10,000 次配對 bootstrap；seed 固定為 2026111668，每次保留整群後計算 query 平均。上述是名目 95% 雙側區間，未作多重比較調整。

- 8B／8B 排序 gap：15.13 pp，單側 95% 下界 11.20 pp，高於事前 2 pp 參考差距。
- `100 − 8B oracle`：28.50 pp，95% 雙側 CI [20.19, 37.37]，單側下界 21.48 pp，也高於 2 pp。
- 後者必須改候選成員或尾序才能回收，包含池外正例及尾序限制，不能全稱純召回損失。機械判讀為 `detectable_remaining_map_gap`。

## 實際成本與完整性

同一張 RTX 3090、torch 2.14／CUDA 12.6、SDPA，無量化或 CPU offload；影像 batch 8、文字 32、cross 4。2B 舊快取須通過 SHA、來源與設定驗收才重用；8B 索引與三組新增重排均重新執行。兩個 8B 模型依序載入，完整正式作業於台北 17:31 結束，return code 0。

|---|---:|---:|---|
| 8B 建索引 | 1239.75 | 20.66 | 8,191 圖＋136 query；2B 索引重用 |
| 2B 重排 | 522.58 | 8.71 | 8B 入池的 6,800 對；舊 2B 入池分數重用 |
| 8B 重排 | 2371.35 | 39.52 | 兩種入池各 6,800 對，共 13,600 對 |

主階段合計 4133.67 秒（68.89 分），另有下載、預檢、smoke 及 CPU 分析。8B 索引／重排 peak reserved GPU 記憶體分別為 17.09／17.67 GiB。這些是離線實驗成本，不能當成線上單題延遲；每題同樣 50 次重排並不等於相同實際算力。2B／2B 的歷史成本沒有在本輪重新計時。

32 個 CPU 合成測試已通過。未實作主分析的審查者另外以 scalar AP、DFS 分群與抽樣頻數矩陣重算，四格逐題指標、所有配對區間／比例／判讀均一致；並核對完整召回排序、候選順序、十份 canonical 陣列 SHA、checkpoint 與實際 BF16 收據。詳見 [獨立審查](2026-11-16-core-scaling-review-codex.md)。

## 研究含義與限制

現有證據支持「CORE 8B 尚未消除本面板的 oracle gap」。後續方法應與本輪較強的 2B 召回＋8B 重排基線比較，並把額外計算成本算入。

這份面板已曝光，標籤由 COCO 類別／面積規則建立，存在語意及完整性限制；群 bootstrap 也未涵蓋所有類別與語意依賴。**oracle 差距不等於可實作方法保證能取得的提升。** 要把本輪診斷升格為研究證據，仍需人工核對錯例與正例，並在未曝光、標註合適的資料上確認。本輪未開啟封存面板、未訓練或擴大方法搜尋。
